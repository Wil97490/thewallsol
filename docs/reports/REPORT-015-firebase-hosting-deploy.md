## 2. Summary

`scripts/deploy.sh` previously stopped after switching Cloud Run traffic;
`firebase.json` was never pushed to Firebase Hosting by anything in this
repository. Added one step, run only after the existing Cloud Run traffic
switch succeeds: `npx firebase deploy --only hosting --project "$PROJECT"
--non-interactive`, using a newly pinned `firebase-tools` devDependency so
the CLI is reproducible rather than fetched ad hoc. On failure the script
exits non-zero with a message distinguishing "Cloud Run is already live and
correct" from "Hosting configuration not published" — it does not roll
back the traffic switch. `DEPLOY.md` was corrected to describe four steps
instead of three, and to name the one new one-time operator prerequisite
(`firebase login`).

Before writing any code, inspected `scripts/deploy.sh` in full,
`package.json`, every other file in `scripts/`, `.github/workflows/ci.yml`
(test-only, confirmed no deploy step exists there), and `firebase.json`
itself, to confirm precisely where the gap was and that nowhere else in the
repository already covered it.

## 9. Gaps

Every acceptance criterion in SPEC-015 §7 that depends on a real deployment
(criteria 5, 6, and the production half of 8) is **not evaluated here, by
design** — SPEC-015 itself scopes the actual deploy and production
verification out of its own implementation, requiring a separate explicit
`GO` (§7.5). Additionally, and independently of that scoping choice, a real
deployment could not have been run from this environment even if asked:

- `npx firebase-tools login:list` → `⚠ No authorized accounts, run "firebase
  login"` (measured, read-only, no deploy attempted).
- `gcloud auth application-default print-access-token` → `ERROR: ...Your
  default credentials were not found.` (measured, read-only).
- `gcloud auth list` does show one authenticated account
  (`cryptorunx@gmail.com`), but this is `gcloud`'s own auth store, which
  `firebase-tools` does not read for Hosting deploys — confirmed by the
  `login:list` result above being empty despite that.

What **is** confirmed, measured, read-only, in this session: `npx firebase
--version` runs and reports `15.28.2` after `npm install` populated
`node_modules/.bin/firebase` from the new devDependency — the CLI itself is
present and executable in this environment; only its authentication is
missing. This distinction (mechanism present, credential absent) is the
exact reason SPEC-015 §9's risk section and §11 exist, and the exact reason
this report does not, and must not, claim criterion 6 (the live
`https://thewallsol.com/css/app.css` checks) as PASS.

## 10. Risks

- Firebase Hosting deploy failing after Cloud Run's traffic switch leaves
  the two layers momentarily inconsistent (Cloud Run live and correct;
  Hosting still on its previous configuration). This is the same shape of
  risk the existing Cloud Run preflight-failure path already accepts and
  reports loudly rather than hides; not new to this SPEC's design, applied
  consistently to the new step.
- `firebase-tools@15.28.2`'s own dependency tree carries 10 moderate `npm
  audit` findings (`google-gax`/`gaxios`/`uuid`/`re2`, transitively) — the
  same family already present today from the existing `@google-cloud/
  firestore` optionalDependency, not newly introduced by this pin.
  Pinning `^13.x` instead was tested first and found to add 1 critical and
  1 high finding (`tar`, `uuid`) beyond that baseline; `^15.28.2` does not,
  which is why it is the version pinned. None of this reaches the deployed
  Cloud Run container — `Dockerfile` runs `npm install --omit=dev`, so
  `devDependencies` are never installed there; the exposure, such as it
  is, is local to whichever machine runs `npm run deploy`.
- `firebase deploy` failure modes beyond auth (Hosting site name mismatch,
  a project-level Hosting quota, a malformed rule Firebase's own validator
  rejects) have not been exercised — none can be, without a real deploy.

## 11. Requires human validation

- `firebase login` — one-time, interactive, in a browser, on the Google
  account tied to the Firebase project. Nothing in this environment can
  perform this; it is also explicitly out of what `CLAUDE.md §6` allows
  Claude Code to do regardless (no credential handling).
- The real `npm run deploy` run this SPEC's mechanism enables, and the
  post-deploy verification against `https://thewallsol.com/css/app.css`
  specified in SPEC-015 §7.6 — both require a separate, explicit `GO`.
- Merge of the PR this report accompanies.

## 12. Still manual

Firebase Hosting authentication itself: this SPEC makes the deploy *step*
automatic once credentials exist, but provisioning those credentials (via
interactive login, or by wiring a service-account key with the Firebase
Hosting Admin role through `GOOGLE_APPLICATION_CREDENTIALS`, which
`firebase-tools` can use non-interactively as an alternative to `firebase
login`) remains an operator decision this SPEC does not make on their
behalf, and did not attempt.

## 13. Recommended next step

Operator runs `npx firebase login` once (or provisions a service-account
key for non-interactive use), then this PR is audited and, if it passes,
merged — after which a separate explicit `GO` for the real `npm run
deploy` run is the only way SPEC-015 §7.6's production criteria can ever
be measured and reported as PASS.
